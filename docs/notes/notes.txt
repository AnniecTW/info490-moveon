Week 2: Progress Checkpoint
- Original V0 foundation: The Week 2 project began with a front-end mock experience built in V0, including the UI layout, featured bundles, marketplace listing cards, filters, and overall branding for the MoveOn marketplace. These templates and components were designed around a curated, static mock dataset rather than live backend data.
- Architectural limitation of V0: We recognized that the UI had been built with mock data and static values, so it could demonstrate the design but not yet reflect real application data from Django. The project was therefore structurally incomplete as a full-stack app because the front-end was visually complete but not backed by persistent data or a live API.
- Transition from mock data to real Django models: To move the app toward a functional full-stack architecture, we shifted focus from purely visual development to data modeling in Django. We defined the marketplace domain objects that corresponded to the real business needs: users, item categories, item types, listings, and related listing metadata. This step marked the architectural change from a static V0 design to a model-driven Django application.
- Model implementation and schema evolution: We updated the data model so listings had the proper fields required by the marketplace, including title, seller, item category/type, price, condition, bundle eligibility, and image support. We added an actual image field to the Listing model while keeping the earlier image_url field in place to avoid breaking existing assumptions and to support a gradual migration instead of a hard cutover.
- Media configuration and file handling: We configured Django media storage so image files could be stored and served correctly. This was necessary because the real application needed to support uploaded listing images, not just URLs or placeholder assets. We also kept the model compatible with realistic file storage while maintaining the old field for compatibility.
- Data migration from V0 content to Django records: We reviewed the V0 mock values and translated them into actual Django rows. Instead of only displaying the mock examples in the frontend, we seeded the database with real marketplace records, ensuring each listing was backed by model instances, relationships, and saved data. This included migrating the V0 item content into actual seller, category, item type, and listing records.
- Seed command workflow: We preserved the existing seed_demo_data functionality and created the needed logic to populate the database with realistic data from the V0 source content. This allowed the application to have realistic records when testing the app without manually creating each entity by hand. We also validated that the seeded objects matched the required conditions and relation structures.
- Django backend API design: Once the database had actual listings, we built the Django API endpoint at /api/listings/ so the frontend could request a real JSON payload from the backend. The endpoint assembled the listing details from the database and returned fields like id, itemName, title, imageUrl, originalPrice, salePrice, condition, category, itemType, seller, and bundleEligible. This gave the front-end a real data contract instead of static JSON or fake dataset values.
- Front-end integration change: The key architectural change was in the frontend: instead of relying only on V0 mock data and static UI state, the marketplace app was updated to fetch the live listings from Django. The component originally designed around mock content was adapted to call the API endpoint, await the response, normalize the payload into the frontend Listing shape, and then render the results using the existing V0 UI structure.
- Adjustment to UI expectations: Because the V0 front-end had been built around a particular shape of data, we had to normalize the Django payload before rendering. Fields such as condition, image URL, seller name, and display values needed to be converted or defaulted so the listing cards still fit the current UI layout. This was a critical step because the design already existed, but the data from Django had a different shape and naming structure.
- CORS and environment configuration: We encountered issues where the frontend and backend were running on separate ports and the browser blocked requests from one domain to another. To fix this, we installed and configured django-cors-headers and verified the backend could accept requests from the frontend origin. We also moved the secret key management to environment variables using .env so sensitive configuration was not hard-coded into the project.
- Debugging the runtime environment: We ran into several practical issues during the integration process: Windows path and shell syntax problems, port conflicts, the frontend trying to run before the backend was available, and the need to restart Django after making code changes. We solved these by validating the correct commands for the local environment, using the proper Python and PowerShell context, and restarting the backend when the API was not yet listening.
- Verification with live data: We verified the architecture by hitting the live Django endpoint directly and checking the returned JSON. The backend responded with a real record set, including actual listing titles, prices, and seller details. We then confirmed the frontend page at localhost:3000 loaded the same listing data in the UI, proving that the application had moved from mock V0 content to real database-backed content.
- Final state: The project is now in a hybrid but functional state: the V0 UI and templates remain the visual shell, but the data layer is live and sourced from Django. The front-end fetches from the backend API, the content is generated from real database rows, and the site behaves like a real full-stack marketplace instead of a static mock demo. This was the major architectural shift that took the project from the original Week 2 V0 version to the current integrated application.

Initial project setup and branch strategy:
- Project initialization and environment structure: The first part of the assignment focused on setting up the Django project structure correctly. We created a clean separation between the development and production configuration files so the project could follow Django best practices, instead of keeping everything in a single settings file. The settings were organized under moveon/settings/, with base.py used for shared configuration, and separate development.py and production.py files for environment-specific behavior.
- .env and secret management: We created an .env file at the project root and stored the SECRET_KEY there instead of hard-coding it into the repository. This kept sensitive configuration out of the codebase and made the project easier to configure across different environments. The environment loader then read the value from .env when Django started up.
- Restructuring the project folders: We confirmed that the project layout needed to reflect the real application architecture. The main Django app, marketplace/, was kept in the project root, while configuration for the project itself lived under moveon/. We also ensured the BASE_DIR and path references were correct so imports, template discovery, static files, media files, and environment loading all resolved properly.
- Branch strategy and collaboration workflow: The week 2 branch was created by cloning the main branch at the project state that reflected the endpoint and work completed on the week 1 branch. This meant the week 2 branch started from the latest shared baseline rather than from an isolated local copy. After the first phase of the assignment was completed — including the folder restructure, environment setup, and configuration updates — the work was pushed back to the week 2 branch.
- Purpose of the week 2 branch model: Once the base project structure and environment were stable, each team member could clone the week 2 branch into separate working branches and divide the remaining work by feature or by task. In practice, this allowed one developer to work on Django view logic while another worked on templates, data migration tasks, or frontend integration, while still staying aligned with the shared week 2 branch as the main integration point.
- Final merge flow: The individual branch work was then expected to be merged back into the original week 2 branch, where the integrated app would be validated. After the team was satisfied with the combined result, that week 2 branch could then be merged back into the main repository branch.

Assignment requirement satisfaction:
- Required view locations: The four assignment-required Django views are implemented in marketplace/views.py. This file contains both the Function-Based Views and the Class-Based Views required for the grading checklist.
- Purpose of each required view:
  - manual_http_response: This is a Function-Based View that manually returns raw HTML using HttpResponse. It demonstrates a direct response without using the render() shortcut and is intended to show a low-level Django view implementation.
  - render_listing_summary: This is a Function-Based View built with render(). It fetches listings from the database and passes them into a template context to display the listing summary in a rendered HTML page.
  - BaseListingView: This is a Class-Based View built from Django's View class. It implements get() and handles the queryset and template rendering explicitly within the class method.
  - GenericListingList: This is a Class-Based View built from Django's ListView generic view. It uses the Listing model, a template name, and a standard list context so the page is produced in a more conventional generic CBV pattern.
- Associated URL locations: The routes are defined in marketplace/urls.py. This file maps the URL patterns to the names of the views and is the place to look for the view endpoints used in the assignment.
- Working route mapping:
  - /students/manual/ -> manual_http_response
  - /students/render/ -> render_listing_summary
  - /students/cbv-base/ -> BaseListingView
  - /students/cbv-generic/ -> GenericListingList
- Template support: The HTML pages used by the render-based and CBV-based examples are stored in the marketplace/templates/marketplace directory, including render_listing_summary.html, base_listing_view.html, and generic_listing_list.html. These templates render the listing information in the corresponding format for each view type.
- Validation and proof: The requirement was verified by running Django's project checks and the project test that confirms the required routes resolve successfully. The project system check reported no issues, and the specific test for the required view URLs passed, confirming that the assignment requirements were satisfied in code and in practice.
